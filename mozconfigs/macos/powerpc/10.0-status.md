# Mac OS X 10.0 deployment work

The required PowerPC goal is 10.0 through the later PowerPC Mac OS X releases.
There is no validated 10.0 application/platform build yet. The 10.3.9 profiles
are intermediate build targets, not a claim of the required minimum.

## Concrete results

* The pinned Linux Apple GCC 4.0.1 toolchain accepts a 10.0 compiler target.
* Apple's original 10.0 startup sources compile. The authoritative revision is
  [Csu 8097534](https://github.com/apple-oss-distributions/Csu/tree/809753418c8044b256903fa84f03e69f1b5531a7),
  selected by Apple's `distribution-macOS` tag `mac-os-x-100`.
* Small C++ and Cocoa Objective-C++ executables link with that startup code,
  flat-namespace loading, and no modern C++ runtime dependency. Their Mach-O
  headers contain `DYLDLINK` without `TWOLEVEL`, `WEAK_DEFINES` or
  `BINDS_TO_WEAK`; their entry command is `LC_UNIXTHREAD`.
* The Cocoa probe compiles with both availability bounds set to 1000 and links
  only Cocoa and libSystem. Its `--foundation-only` mode ran on original 10.0
  build 4K78 under QEMU PowerPC emulation, printed `Early Cocoa probe: 42` and
  exited with status 0. Full GUI initialization and physical hardware remain
  untested.

The initial probes used the archived **10.1.5 SDK**. A subsequent Cocoa probe
links against libraries from the original Mac OS X 10.0 retail installation CD,
build **4K78**, using 10.1.5 headers with both availability bounds set to 1000.
Its direct dependencies are Cocoa 5.0.0 and libSystem 50.0.0. The private
CFNetwork and SystemConfiguration framework locations must also come from
10.0, since their locations changed in the later SDK.

The CD image was verified against SHA-1
`23d00b0d6ec621a997b423d89dedd52db1da119b` and mounted read-only. The temporary
SDK overlay records its provenance; copied private-framework files were also
SHA-256 compared with the CD. This is still an experimental overlay with later
headers, not an original developer SDK or a complete installed OS. The small
Foundation-mode runtime pass does not establish complete platform support.

## Open constraints

* A separate template test now passes on original 10.0 under emulation: an
  executable and two shared libraries see the same function-local static
  integer (`coalescing: same=1 value=42`, exit 0). The binaries retain GCC's
  `WEAK_DEFINES` and `BINDS_TO_WEAK` flags. This bounds the evidence to that
  case; general weak/strong-symbol resolution and full C++ ABI behavior remain
  unvalidated. Absence of declarations in the early headers alone did not
  establish a runtime failure.
* A matching GCC C++ ABI runtime prototype now passes allocation, RTTI,
  exception/destructor unwinding, throwing-initializer retry and eight-thread
  static-initialization tests on 10.0. See [early-cxx-runtime.md](early-cxx-runtime.md).
  Full libstdc++ and platform integration remain unfinished; Panther's system
  C++ libraries cannot be assumed present on 10.0. Preserve thread-safe
  initialization and exception semantics while completing this work.
* The stock classic linker rejects a literal 10.0 deployment value. The narrow
  `build/macosx/odcctools-10.0.patch` fixes its parser and guards the host-only
  sysctl call for Linux. `build-early-ppc-linker.sh` rebuilt it from a pinned
  source archive in 32-bit Linux; the resulting linker passed the original
  10.0-library Cocoa probe with a literal 10.0 target. It stays separate from
  the Panther toolchain. Neither linker encodes minimum-OS metadata in these
  old objects, so the accepted target alone is not a deployment audit.
* Cairo/ATSUI, Cocoa widgets, printing, NSPR and filesystem APIs need an early
  availability audit. Preserve historical application APIs through fallbacks.
* Full Suite, Browser, Calendar and XULRunner builds, target runtime checks,
  and the Linux GitHub Actions/act matrix remain outstanding for 10.0.

## Early SDK preparation

The early linker requires the container's `libssl-dev`, `uuid-dev` and `patch`
packages in addition to the existing build prerequisites. Given the upstream
`odcctools-20090808.tar.bz2` archive, build it with:

```sh
sh build/macosx/build-early-ppc-linker.sh /downloads/odcctools-20090808.tar.bz2 /tools/early-ppc
```

The script checks the archive SHA-256, applies the patch, and installs `ld`
for direct invocation. The pinned GCC driver's hard-coded linker path overrides
`-B`, so compile objects separately from this link step. The script refuses to
overwrite an existing linker. Original 10.0 Csu startup code, target libraries
and flat-namespace linking remain necessary; this command does not build an
application or supply its C++ runtime.

Rebuild the matching original 10.0 startup object with:

```sh
ZR_PPC_DEPLOYMENT_TARGET=10.0 \
ZR_PPC_EARLY_LINKER=/tools/early-ppc/ld \
ZR_MACOS_SDK=/sdks/experimental-10.0-overlay \
sh build/macosx/prepare-ppc-startup.sh
```

This downloads checksum-pinned original Csu sources and installs
`crt1.o`, `dylib1.o` and `bundle1.o` under
`/opt/mac/lib/zoolrunner-cheetah`. The script passed in a fresh toolchain
container, and the resulting startup object passed the original-library Cocoa
link probe. The default startup target remains the intermediate Panther port.

`build/macosx/tests/link-early-cocoa.sh OUTPUT_BINARY` reproduces the probe
using the same `ZR_MACOS_SDK` and `ZR_PPC_EARLY_LINKER` variables. Its checked-in
Objective-C++ source exercises Cocoa initialization and a simple out-of-line
C++ class. It deliberately does not test templates, exceptions, allocation or
static-initialization guards. The script links and prints Mach-O metadata;
execution on the actual OS is a separate required test.
Use `--foundation-only` in a single-user shell without WindowServer. That mode
exercises an autorelease pool, Objective-C messaging, NSLog and the C++ class.
The default mode additionally creates NSApplication and remains untested.

The initial runtime attempt exposed duplicate startup-hook definitions because
GCC silently invoked ld64 despite `-B`. The corrected script compiles the object
and invokes the rebuilt classic linker directly; the corrected executable
passed the 10.0 Foundation-mode runtime check.

`build/macosx/tests/link-early-coalescing.sh NEW_OUTPUT_DIRECTORY` builds the
shared-template test with the same SDK/linker variables and original 10.0
`dylib1.o`. Run `coalescing` beside its two libraries on the target OS. The
checked-in script's final output was executed successfully on original 10.0.
This test uses constant initialization;
it does not exercise C++ static-initialization guards or exception handling.

For C++ exception handling, the 10.0 startup preparation also includes GCC's
`crt2.o` and a small bridge that performs its pre-10.2 frame registration after
the original key-manager initialization. This follows the initialization order
in Apple's later Csu. Without it, the C++ exception probe aborted despite a
successful link. The original Csu archive remains checksum-verified; this
compiler integration is an explicit addition rather than an OS-file patch.

An exploratory comparison of imports from 106 Panther runtime binaries against
the original libraries identifies early-OS work in ATSUI direct layout and font
fallbacks, bitmap-context accessors, Quartz shading, keyboard-layout APIs,
POSIX functions and C++ support. Some calls already have deployment guards;
this comparison is a work list, not proof that each needs a new fallback.
Original AGL and QuickTime binaries were taken from the CD's Essentials package
without executing installer scripts. Objective-C method availability, dynamic
lookup and per-library binding still require separate checks.

Repeat the exploratory comparison with:

```sh
python3 build/macosx/survey-ppc-imports.py /build/dist/bin /sdks/experimental-10.0-overlay \
  --nm /opt/mac/bin/powerpc-apple-darwin8-nm --report /build/import-survey.json
```

The report records unavailable-symbol candidates per binary. A symbol present
somewhere in the overlay might still be unavailable through a binary's actual
dependencies, so an empty candidate list would not prove correct loading.

`build/macosx/fetch-sdk.sh DESTINATION 10.1.5` downloads a checksum-pinned
archive. Its OpenStep-format metadata is validated without conversion. The
private SDK copy receives a narrow patch changing the obsolete
`extern "Objective-C"` block in `NSJavaSetup.h` to `extern "C"`; GCC 4 rejects
the old spelling. The SDK's exported symbols use the corresponding unmangled
C names. No application-facing Java bridge declarations are removed.

The SDK archive is about 5 MB. Keep SDKs and probe output separate from existing
developer builds, and remove completed local matrix workspaces after saving
their artifacts and logs.

## Original-OS boot experiment

QEMU 11.1.1 on an arm64 Mac booted the original 4K78 filesystem through kernel
startup to the graphical language-selection installer. The archived image is
an unpartitioned HFS wrapper around HFS+, which OpenBIOS could not load directly.
`build/macosx/tests/wrap-10.0-cd.py` adds a 32 KiB Apple partition map before
the unchanged filesystem payload. The payload SHA-1 still matches the archived
image; no OS files are patched. The script's output was byte-compared with
the successfully booted wrapper. The additional image occupies about 565 MiB.

```sh
python3 build/macosx/tests/wrap-10.0-cd.py original-10.0.cdr mapped-10.0.cdr
qemu-system-ppc -M mac99 -cpu G3 -m 256 \
  -drive file=mapped-10.0.cdr,media=cdrom,index=2,format=raw,readonly=on \
  -net none -prom-env 'boot-device=cd:2,\SystemFolderX\BootX' \
  -prom-env 'boot-args=-v'
```

This uses QEMU's documented [PowerMac emulation](https://www.qemu.org/docs/master/system/ppc/powermac.html).
Reaching the installer validates the emulated boot environment only. For the
subsequent probe run, a separate 16 MiB HFS+ test volume held the executable.
Booting with `boot-args=-s` provided a single-user shell. The probe volume was
mounted read-only at `/tmp`, and `/tmp/early-cocoa --foundation-only` printed
the expected value and returned 0. This validates that bounded probe, not
ZoolRunner or physical PowerPC hardware.
